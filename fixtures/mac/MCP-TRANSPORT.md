# macOS Copper MCP transport contract

Captured from the running macOS Copper `1.0.20261008.48` at `http://127.0.0.1:4123/mcp` on 2026-10-12. The fixtures are JSON-RPC response envelopes: [`mcp-initialize.json`](mcp-initialize.json), [`tools-list.json`](tools-list.json), and read-only, scrubbed [`browser_tabs_list.json`](mcp-examples/browser_tabs_list.json) / [`jev_observe.json`](mcp-examples/jev_observe.json). Tool names in `tools-list.json` are sorted; its 45 tools arrived in one page (no `nextCursor`). Example tab URLs and titles were replaced with `https://example.test/...` and `Title n`; tab identifiers, group names, control labels and values were also replaced. The examples retain the response structure and display syntax, not the user's page data.

## HTTP exchange observed

- Streamable HTTP: JSON-RPC 2.0 requests are individual `POST /mcp` messages with `Content-Type: application/json`, `Accept: application/json, text/event-stream`, and `Authorization: Bearer <token>`. Successful replies are **JSON, not SSE** (`Content-Type: application/json`); the server does not provide an event stream. Authenticated `GET /mcp` returned HTTP 405 and `{"error":"no event stream — POST JSON-RPC messages here"}`. The listener is loopback-only.
- `initialize` (`protocolVersion: 2025-06-18`, `clientInfo` supplied) returned HTTP 200 and a JSON-RPC `result` with `protocolVersion`, `capabilities`, `serverInfo` and `instructions`. Response headers: `Content-Type: application/json`, `Content-Length: 2931`, `Cache-Control: no-store`, **`Mcp-Session-Id: <server-generated UUID>`**, `Connection: keep-alive`. The session ID's value is deliberately not in the fixtures. Preserve it and send it as `Mcp-Session-Id` on subsequent requests.
- `notifications/initialized` (no JSON-RPC id, session header supplied) returned HTTP 202, zero-length body, `Content-Type: application/json`, `Content-Length: 0`, `Cache-Control: no-store`, `Connection: keep-alive`. Notifications have no JSON-RPC response.
- `tools/list` (session header supplied) returned HTTP 200 with a JSON-RPC `result.tools` array, `Content-Type: application/json`, `Content-Length: 32921` for the **unsorted wire response**, `Cache-Control: no-store`, `Connection: keep-alive`. No `Mcp-Session-Id` response header on this call; no pagination cursor on this build. A client should still follow `result.nextCursor` with `params.cursor` if one appears. The pretty-printed sorted fixture has a different byte length from the wire response.
- `tools/call` for `browser_tabs` with `{"action":"list"}` and `jev_observe` with `{"text":false,"limit":10}` each returned HTTP 200 with `result.content: [{"type":"text","text":"..."}]` and `result.isError: false`. Both calls only read the browser. The first text is a Markdown open-tab list; the second is `### Page`, `### Elements` and indexed controls with no visible-text section.

### Authentication and Origin errors (observed)

All error responses below were JSON over HTTP with `Content-Type: application/json`, `Content-Length`, `Cache-Control: no-store`, `Connection: keep-alive`. They are **plain HTTP error objects, not JSON-RPC `error` envelopes**:

| Request | HTTP | Complete JSON body |
| --- | ---: | --- |
| `POST /mcp` with bogus bearer, no Origin | 401 | `{"error":"bearer token required — Settings › Agents"}` |
| `POST /mcp` with valid bearer, `Origin: https://evil.test` | 403 | `{"error":"forbidden origin"}` |
| Bogus bearer **and** `Origin: https://evil.test` | 403 | `{"error":"forbidden origin"}` |

Origin is rejected before authentication. The source allows loopback `Origin` values containing `://127.0.0.1` or `://localhost`; other Origins are forbidden. JSON-RPC dispatch errors (e.g., unknown method) are a different, in-band `{"jsonrpc":"2.0","id":...,"error":{"code":...,"message":...}}` shape.

## Source contract (`Fork/MCP/MCP.swift`, `Bridge.swift`, `Hands.swift`)

- **Port and token:** `MCP.Config` is saved at `Store.file("agent.json")` with POSIX mode `0600`; this Mac's file was verified `0600`. Actual top-level keys seen (names/types only): `enabled` (Boolean), `port` (integer), `token` (string), `announces` (Boolean), `jev` (Boolean), `links` (array). Link entries expose key names `announces`, `api`, `enabled`, `id`, `label`, `linkId`, `name`, `token`; an optional legacy `agentLink` object may be emitted for a matching legacy link. **No `agent.json` field values or secrets are copied into these fixtures.** A newly generated bearer is 32 random bytes encoded as lowercase hex; default port is `4123`, path `/mcp`, and `SEARCH_MCP_PORT` overrides the listener port for that process without changing the file.
- **`--mcp-stdio`:** The same Copper executable enters `Bridge.runIfAsked` before constructing the app window. It reads one JSON-RPC line at a time from stdin, POSTs each to the already-running loopback HTTP server with the file's bearer and an `X-Copper-Agent` identity header, then emits a compact JSON line per reply on stdout; HTTP 202 notifications produce no stdout line. It reads `agent.json` (`enabled`, `port`, `token`), checks `/health`, and, if no process exists, launches the app without activating it and waits up to 12 seconds for the port. If Copper is already quitting it waits rather than launching a racing instance, then rereads the config in case the token rotated. `SEARCH_MCP_PORT` applies here too. If startup or transport fails, it returns a JSON-RPC `-32000` error to requests with ids. The bridge does **not** forward an HTTP `Mcp-Session-Id`; its persistent per-process `X-Copper-Agent` identity distinguishes its calls instead.
- **Caller identity (`Drive.Who`):** Direct HTTP clients receive a lowercased UUID `Mcp-Session-Id` on `initialize`, which the server uses to associate `clientInfo.name` and initialization metadata with later calls. Each request may also send base64-encoded JSON in `X-Copper-Agent` (the bridge/CLI obtains it from agent environment: label/thread/session/harness, project folder, bridge instance, etc.) and/or `params._meta["copper/agent"]` (which overrides header fields). Per-request fields override what was remembered at initialize. `Drive.Who.from` chooses the displayed agent from explicit label, then client name, harness, client, or fallback; chooses session from explicit agent session, bridge instance, or MCP session ID; derives a stable hand key, thread/project caption and colour seed. The transport does not require an ongoing server-side MCP session to dispatch methods: the minted header is principally a caller-identity key, and `clientName` alone is only a last-resort fallback.
